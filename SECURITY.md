# Security model and scope

auditrail is an early-stage project (v0.2, no independent security review). This
document exists so nobody -- including us -- overestimates what it does. Each
claim in the "does" column is covered by at least one test (named in
[docs/STATUS.md](docs/STATUS.md)), **except for the cases listed under "Where the
tests do not reach" below**; every gap we know of is in the "does not" section. It maps features to the OWASP Top 10 for Agentic Applications 2026
(ASI01-ASI10) and to the "lethal trifecta" framework (Simon Willison).

**The one-sentence version:** auditrail makes a record of what an agent did that
the operator cannot quietly rewrite, *if you keep the signing key and a witness
copy out of the operator's reach* -- and it tells you plainly what it did not check.

## What v0.2 does

| Feature | Maps to | What it proves, and the condition |
|---|---|---|
| Hash-chained ledger (`ledger.py`) | forensics for any ASI category | Records were not edited, reordered or inserted **by someone who did not also recompute the hashes**. On its own this is tamper-*evident* only against accidents. |
| Ed25519-signed records (`keys.py`, `recorder.py`) | evidence integrity | A rewrite also needs the recorder's private key. **Holds only if the agent and the operator cannot read that key** (see "Key custody"). Verified with `verify --pubkey`; without a key the verifier says signatures were not checked. |
| Anchors + witness (`anchor.py`) | evidence integrity | Records up to the last anchor were not removed or rewritten, **if a copy of the anchor lives somewhere the operator cannot alter** (public git repo, timestamping service, customer storage). A verifier holding only the witness copy needs nothing from the operator. |
| Heartbeats (`Guard.heartbeat`, recorder) | completeness (partial) | Shows silent periods, tool-list and policy changes over time, and calls that a running writer intercepted but failed to record (the count is carried to the next heartbeat if a heartbeat cannot be written). It covers **only wrapped tools**. **Not covered:** the counts live in the writer's memory and a call's record is written after the tool returns, so if the process dies inside a tool (a kill, an out-of-memory stop, a power cut) the side effect may have happened with no record and no count, and no later heartbeat will say so. A token holder can also write a record of kind `heartbeat`, and the recorder signs it, but it carries `origin: "client"` inside the signature; the recorder's own heartbeats and anchors carry no `origin`, so the two can be told apart (a client's heartbeat that is well formed but untrue cannot be refused). |
| Independent *implementation* of the verifier (`verifier/`, Rust; **same author**) | -- | A separate implementation, checked against the same conformance vectors and fuzzed against the Python one, so the format does not depend on our Python. Both read files by the same strict rules (spec section 2). The same author wrote both, so this is a consistency check, not yet independent review. |
| Lethal-trifecta policy engine (`policy.py`) | ASI02, ASI03 | Blocks a tool call *before it runs* if it would complete data-access + untrusted-input + external-comm within one **workflow**: sessions that share a `trace_id`, or agents linked by a signed message that carries the sender's categories. Checking and reserving the categories is one locked step at admission, so tools started at the same moment in one workflow cannot all pass; the reservation is kept even if the call then fails (it may have touched data first). The state lives in one `PolicyEngine`, i.e. one process: separate processes sharing a `trace_id` do not see each other's calls. |
| Per-agent Ed25519 messages, receipts, `reconcile` | ASI07 | A message is attributable to one agent (not "anyone with the shared secret"), is bound to its recipient, and both sides' ledgers can be cross-checked for a message only one side recorded. |
| Process-isolated tools (`isolate=True`) | partial ASI05 | Runs a call in a subprocess with an **allow-listed** environment and a timeout. Reduces accidents and ambient-secret leakage. |

## What v0.2 does NOT do

Be skeptical of any tool (including this one) that does not say this part out loud.

**About the evidence**

- **It cannot prove a tool call was recorded if the tool was never wrapped.** Heartbeats list only wrapped tools. Completeness needs an architecture in which the agent holds no outbound credential except through the guard, plus cross-checking with the called system's own logs. auditrail gives you the pieces, not that architecture.
- **Records after the last anchor are not covered.** `verify` reports exactly how many.
- **Nothing helps if the recorder host or key is compromised.** `auditrail recorder` is a separate *process*. Running it as the same OS user as the agent protects against the agent's code, not against anyone who can read that user's files. Use a separate OS user, host, or KMS/TPM.
- **The witness must be independent.** An anchor only the operator holds is just a line the operator can delete. Colluding witnesses defeat it.
- **Anchors you never publish prove nothing.** `anchor` without `--git-repo`/`--witness-file` is local only, and says so.
- **No dependency on trusted time.** Timestamps are the recorder's clock; a timestamping (RFC 3161) witness is not implemented yet.
- **Args and results are stored as digests only.** That protects privacy and also means the ledger cannot reconstruct what was said. Encrypted retention is not implemented.

**About the policy and messages**

- **No prompt-injection detection, and none of the content of a message is judged.** A signed message can carry an injection; signatures prove origin, not safety.
- **The trifecta rule is category-based and the categories are labelled by you.** A wrong label defeats it. A write action with no external-comm label (rerouting a shipment, issuing a refund) is not blocked by it. Two opt-in options reduce this (see "Opt-in hardening" below); they do not remove it, and the defaults are unchanged.
- **Workflow tracking needs the link.** Two sessions with different `trace_id`s and no signed message between them are still independent (the known gap in the simulation).
- **Categories that arrive with a signed message are counted, not name-checked.** A sender's workflow categories are another policy's data; they feed the trifecta and state_change rules by exact string. A misspelt category from a peer (`State_Change`) therefore protects nothing in the receiver, and a peer cannot be made to declare names with `custom_categories`. Compare policies across agents out of band.
- **Messages need your key registry to be right.** Whoever controls the registry decides which key speaks for which agent. The v1 shared-secret HMAC remains for compatibility and **proves only "someone with the secret"**.
- **Replay protection is in memory by default.** `ReplayGuard` is per process and forgets nonces after its TTL (which must be at least the freshness window). `SqliteReplayGuard` shares the memory between processes **on one host**; it does nothing across hosts, and the SQLite file must not live on a network filesystem. A store you operate yourself is needed for a multi-host deployment.

**About isolation**

- **`isolate=True` is not a sandbox.** It is an OS subprocess that shares the filesystem (including `~/.aws`, `~/.ssh`, any credential file) and the network. It stops hangs and inherited environment variables, not a hostile tool. A real boundary needs a container or microVM (see ROADMAP).
- **The environment filter is an allow-list** (`PATH`, `TEMP`, locale, ... plus names you pass in `env_passthrough`). It does not look inside files or other channels.

**About scope**

- **No supply-chain verification (ASI04), no memory/context-poisoning detection (ASI06), no cascading-failure containment (ASI08)** beyond what the above gives.
- **No steganography detection.** There is no known technique that guarantees it; the ledger is an evidence layer for after-the-fact analysis, not a detector.
- **`auditrail report` is a rendering of the verifier's output, not new evidence.** It adds no check of its own: its overall status is the verifier's, it is not signed, and its wording is a fixed table plus a vocabulary test, not a review of every sentence. Its exit code is 0 only when the main ledger and every supplied check (peer ledgers included) found nothing, 1 for any finding or inconclusive result, and 2 when an input or the output could not be read or written. Read the report together with the evidence and the witness copy, not instead of them. `--redact` replaces names in the fields that carry them with codes that are not secrets (a guessable name can be recovered, and policy versions, timestamps and counts stay visible); it is not anonymisation. A salt given with `--redact-salt` travels on the command line, so it shows in the process list and in shell history.
- **Not a certified compliance product.** Nothing here has had an independent audit. Do not represent its output as satisfying NYC Local Law 144, the EU AI Act, ISO/IEC 42001 or any other requirement without your own legal and compliance review.

## Where the tests do not reach

Stated so that "has a test" is not read as "is verified everywhere":

- **Inconclusive results and the algorithm-mismatch rule.** `UNSUPPORTED_ALGORITHM` and `UNSUPPORTED_FORMAT` are failures (exit 1) that someone without the key can provoke by editing a field, so they never mean "untouched" and never outrank a definite finding (conformance vectors 25-36). **Handled (D-14):** a record or anchor that claims an algorithm other than its trusted key's is `BAD_SIGNATURE` ("algorithm mismatch"), implemented or not, so an edit in the unanchored tail with every following record given a `sig_alg` is tamper-grade (vectors 33-36), which was the one case that had stayed inconclusive. **Consequence:** `UNSUPPORTED_ALGORITHM` is unreachable from `.pub` file input, because every such key is Ed25519; it exists for a verifier whose trusted keys carry an explicit type (the Python `TrustedKeys` API). `UNSUPPORTED_FORMAT` remains reachable and inconclusive: the signature of such a record is still checked (so editing a field and re-hashing without the key is `BAD_SIGNATURE`) and a witness or anchors file outranks it, but with no keys and no anchors a ledger whose records say `format` 3 and whose chain holds is reported only as `UNSUPPORTED_FORMAT`, which is also all that can be said of a genuinely newer format. **Scope of the mismatch rule:** it applies when the record's `key_id` resolves to the trusted Ed25519 key. A writer using a *different* key (its own `key_id`) is `UNKNOWN_KEY` under file input, as for any foreign key (both verifiers; measured), and a `.pub` file that is not exactly 32 bytes is refused before verification (Rust: "public key must be 32 bytes", exit 2). **With a witness copy and no keys**, a change to records *after* the last witnessed anchor (the tail) cannot be detected, and the result is `OK` with a note that signatures were not checked; this is the long-standing limit of the format, unchanged from before D-11. A consumer of the JSON output must not assume `unchecked_algorithms` exists in every report (Rust always prints it, Python only on `OK` and `UNSUPPORTED_*`).
- **Algorithm agility is reserved, not implemented.** Only Ed25519 exists. `sig_alg`, `anchor_version` 3 and `UNSUPPORTED_ALGORITHM` define how a *future* algorithm would be named and refused by verifiers that lack it; nothing here lets auditrail produce or check another algorithm, and nothing makes it interoperable with other audit-trail formats. **A verifier built before this change** (measured on `main` before D-11, Python and Rust) returns **`OK`** for a record that carries a `sig_alg` while its signature is a valid Ed25519 one (it ignores the member: conformance vector 16), and likewise `OK` for `format` 3 when the chain holds; it returns `TAMPERED_ANCHOR` for any `anchor_version` 3 line. So the first is *not* fail-closed. Mixed deployments: **upgrade the verifiers first, then the writers**; a writer that starts using another algorithm while old verifiers are still in use would be read as unchanged by them. The "verifier knows an algorithm the other does not" and "record names an algorithm its trusted key is not" paths are exercised with an injected test-only algorithm in Python; no real second algorithm has been run through either verifier.
- **Platforms.** The maintainers' test runs so far were on Windows 11 with Python 3.11. Anything that is
  POSIX-specific has not been executed by us: the permission check on real files (`chmod` modes), the `fcntl`
  file-lock path, a recorder shut down with SIGTERM, and `anchor --push` on a system with a stricter git
  `safe.directory` policy. The pure functions behind them are tested; the end-to-end paths are not.
- **Constant-time token comparison.** A test shows the comparison goes through `hmac.compare_digest` on equal-length
  digests. Nothing measures timing.
- **Key rotation (Key custody, step 5).** "Anchor under both keys for an overlap" is a procedure we describe. There is
  no test that rotates a key and verifies across the overlap.
- **Timestamping services as a witness.** The anchors row lists one as an example of an independent copy; no
  timestamping witness is implemented (RFC 3161 is on the roadmap). Only file and git witnesses exist and are tested.
- **The release workflow** (`release.yml`) has never run on GitHub, so the prebuilt binaries, checksums and
  attestations described in the README are unproven. `verify --git-repo` through the CLI has no test of its own.
- **Tests that need the Rust binary** skip with an explicit reason when it is not built; a green run without it says
  nothing about Python/Rust agreement.
- **The Windows ACL check** reads only the broad groups (see the recorder row below); a loose permission it cannot see passes. It also does not look at the **parent directory** of the ledger or key, and a grant to one specific other account (as opposed to Everyone/Users/Authenticated Users/Guests/Anonymous) is not flagged. The check **failed outright when pytest was started from PowerShell 7** (the child Windows PowerShell 5.1 inherited PS7's module path and could not load `Get-Acl`); it now uses .NET calls only, drops the inherited `PSModulePath` and starts 5.1 by its system path, and this is verified only by a local simulation and by CI, not by every host setup. A PowerShell run that *succeeds but prints nothing parseable* is now treated as `NOT CHECKED` (the recorder refuses to start without `--allow-loose-permissions`); that case used to pass silently. A line that mentions a broad group (its SID or name) but is not a well-formed entry (non-numeric or hex rights, a missing or extra column, spaces around the `|`, lower-case `allow`, garbage around the SID) also makes the file `NOT CHECKED`, however many good lines are next to it. **Lines that mention no broad group and are malformed are ignored**: they cannot be told apart from noise, and the check does not claim to have read them.
- **Key files.** `load_public_keys` (Python) used to accept `.pub` files the Rust verifier refuses (embedded whitespace or newlines, any length) because it used `bytes.fromhex`. It now applies the Rust rule: trimmed text must be exactly 64 hex digits (either case); twenty variants are checked in both languages (`tests/test_t017_pubkey_files.py`). **The private key loader (`Signer.from_file`) is still the lenient `strip()` + `bytes.fromhex`**: it accepts embedded whitespace in a seed. That is a local file you wrote, not evidence, and a wrong length is still rejected by the key library, but it is not the strict rule.
- **Cross-section label consistency is enforced when a tool is wrapped** (`Guard.guarded_tool`). Calling `PolicyEngine.check` directly, without a Guard, does not compare sections, and an inconsistent policy still *loads*. (Pinned by `tests/test_t015_known_limits.py`.)
- **Duplicate YAML keys are not reported**: PyYAML keeps the last one, so a second `tool_categories:` (or `allowed_tools:`) in the same section silently replaces the first. Review policy files like code. (Pinned by `tests/test_t015_known_limits.py`.)
- **Shutdown paths not exercised**: the recorder's clean shutdown is tested with Ctrl+Break on Windows and, unrun, SIGTERM on POSIX. A console-close event (`CTRL_CLOSE_EVENT`) and a service-manager stop have not been tried; they may skip the final heartbeat and anchor.
  see passes.

## Opt-in hardening: what it mitigates and what remains

Most of these are off unless you turn them on, so an existing policy is evaluated exactly as
before. **Four are behavior changes that apply by default** (labels that contradict each other, category names that are not known, the recorder's permission gate, and the same tool labelled differently by two agents) and are listed under "Behavior changes" below with the way back. "Mitigated" means the problem is smaller or louder, not that it is gone.

| Known problem | Option | What it now does | What still remains |
|---|---|---|---|
| A tool nobody labelled is invisible to the trifecta rule | `PolicyEngine(..., strict=True)` or `strict_classification: true` | A wrapped tool with no category (policy or call site) is refused before it runs and the refusal is recorded as `unclassified_tool`. An empty list does **not** count as a label; a harmless tool must say `internal`. Without strict mode a warning is emitted when the tool is wrapped. **Behavior change:** `internal` together with any other category on the same tool is refused with a `PolicyError` naming the tool and the categories, when the policy is loaded and again when the tool is wrapped (so a call-site label cannot contradict the policy). An empty list is still not a declaration. **Behavior change:** a category name must be a built-in one (`data_access`, `untrusted_input`, `external_comm`, `state_change`, `internal`, `agent_to_agent`) or be declared once in the policy's top-level `custom_categories`; any other spelling (`State_Change`, ` internal`, `state-change`, a typo) is a `PolicyError` at load and at the call site, with the closest known name suggested, in every mode. | **A wrong label is still believed.** A state-changing tool labelled `internal` runs (simulation attack 19). The engine cannot know what a function does. `internal` is a convention, not a verified fact. The warning is emitted once at wrap time, and only to whoever reads the output. The check compares labels with each other only: a tool labelled `internal` **alone** runs, whatever it does, because nothing can tell the label is false. **Declaring a custom category is not vetting it**: a wrong but declared name is accepted, and a category the engine has no rule for does nothing. Names are matched exactly (whole string: a trailing newline or space is not tolerated); the check cannot know what a tool really does. |
| A write action with no external channel (refund, reroute) is not stopped | label the tool `state_change`; per agent `enforce_state_change_after_untrusted: true`, optional `state_change_allowed_tools` | A `state_change` tool is refused once its workflow has touched `untrusted_input`, unless explicitly listed. | **Only for tools you labelled `state_change`**, and only after *untrusted input was labelled as such*. A state change with no untrusted input first is allowed. A tool on the allow list is trusted completely. Splitting a workflow without a shared `trace_id` or signed message (simulation attack 11) still defeats it. It is a rule about *order*, not a judgement of whether the action is right: there is no approval step. |
| Replay protection is per process | `SqliteReplayGuard(path)` | One decision shared by all processes on a host; of N processes given the same message exactly one accepts it. Fails closed if the store cannot answer. | Single host only; SQLite on a network filesystem is unsafe; anyone who can write the file can erase nonces, so its permissions matter. The freshness window still bounds how long a nonce must be remembered. |
| The recorder is protected only by a shared token | constant-time token check; start-up permission check (refuses by default; `--allow-loose-permissions`) | The token is compared as fixed-length digests (a non-ASCII token now also works); non-string tokens are rejected. **Behavior change:** `auditrail recorder` refuses to start (exit code 2) when the signing key is readable by other accounts, or the ledger/anchors are writable by them. With `--allow-loose-permissions` the same findings are printed as warnings and it starts. A check that could not run (on Windows: PowerShell missing, failing or timing out) **also refuses to start**, because an unknown is treated as unsafe; with the flag it is printed as `NOT CHECKED` and the recorder starts. POSIX does not use PowerShell and is not affected. | **There is no socket file**: the recorder listens on a loopback TCP port, so *any local process* that knows the token can write, and anything that can read the environment or the agent's memory has the token. The recorder signs a **statement by whoever holds the token**, not its own observation: it only signs records of a fixed shape (each kind has an exact field set and types; a malformed request is refused, nothing is signed, and it is not counted as a call), and it adds `origin: "client"` inside the signature to every record a client asked for. It cannot see inside the agent, so a well-formed but false statement (a made-up decision, a heartbeat with consistent counts) is still signed, marked as the client's. The token travels in clear text over loopback. The permission check cannot see who the agent runs as, and same OS user for agent and recorder defeats all of it. On Windows it reads the ACL through PowerShell and looks only at the broad groups (Everyone, Users, Authenticated Users, Guests, Anonymous): a key readable by one specific other account, or by a group that is not in that list, **passes** (an entry for one of those groups that carries a Generic read/write/all bit is counted as loose, since the check cannot tell whether it was mapped); if PowerShell's listing contains any byte outside plain ASCII (the script prints only SIDs, `Allow`/`Deny` and numbers) the whole listing is refused and the file is `unchecked`, because decoding it leniently could hide an entry; if PowerShell is unavailable, fails, or returns nothing parseable, the check did not run and the start is refused unless you pass the flag. Passing the check is not evidence that the key is safe. |

### Behavior changes (these apply without opting in)

| Change | Effect | Way back |
|---|---|---|
| `internal` may not be combined with another category (policy load and tool wrapping) | A policy that labels one tool `internal` and also, say, `state_change` no longer loads; `guarded_tool` raises `PolicyError` for a contradicting call-site label. Previously both labels were accepted and the tool simply carried both. | Remove one of the two labels. There is no switch that re-allows the combination, on purpose: it would make `internal` a way to look classified. |
| `auditrail recorder` refuses to start with a loose key, ledger or anchors file, **or when the permission check could not run** | Exit code 2 and a message naming each file (or the reason the check failed), before anything is read from the key or written to the ledger. | Fix the permissions or the checker, or pass `--allow-loose-permissions`: loose permissions become warnings and an unchecked file is reported as `NOT CHECKED`. |
| A category name that is not built in or declared is refused (policy load, tool wrapping), in every mode | `State_Change`, `INTERNAL`, ` internal`, `state-change`, unknown names and typos raise `PolicyError` with the closest known name. Previously any string was accepted as a category, so a misspelling silently turned a rule off. | Declare your own names once: `custom_categories: [team_billing, ...]` (lower_snake_case) at the top level of the policy. There is no switch that skips the check: a name nobody declared is the typo this exists to catch, and declaring it is one line. |
| One tool labelled differently by two agent sections, **or labelled by one and merely allowed by another**, fails when it is wrapped (`guarded_tool`) | A tool is one function. If `agent a` says `[data_access]` and `agent b` says `[external_comm]`, or `agent b` lists it in `allowed_tools` without a `tool_categories` entry, `PolicyError` names both sections and the fix. An empty label equals no label; a tool mentioned by one section, or labelled identically everywhere, is unaffected. Loading the policy alone is still fine. | Give the tool the same label set in every section that lists it, or take it out of the `allowed_tools` of the section that should not have it. **A call-site label cannot waive this**: `guarded_tool(categories=[...])` does not make a section that allows the tool without a policy label "labelled"; that strictness is deliberate (D-8), and there is no switch to relax it. |
| New verification outcomes: `UNSUPPORTED_ALGORITHM` and `UNSUPPORTED_FORMAT` (verifiers in both languages) | A record or anchor that names a signature algorithm this verifier does not implement (optional `sig_alg`; anchors of `anchor_version` 3) is `BAD_SIGNATURE` when keys were required and the key is an Ed25519 key ("algorithm mismatch"). `UNSUPPORTED_ALGORITHM` (**not OK, exit code 1, inconclusive**) occurs only when the trusted key is explicitly registered as a type this verifier cannot check, which a `.pub` file cannot express. A definite finding (a stale signature, a `REWRITTEN` or `TRUNCATED` against a witness, ...) always outranks it. An integer `format` other than 2 is `UNSUPPORTED_FORMAT`. An explicit `"sig_alg":"ed25519"` is `MALFORMED_RECORD` (`TAMPERED_ANCHOR` in an anchor). Ledgers written today carry no `sig_alg` and are byte-identical and verify as before. | Nothing to go back to for existing ledgers. Scripts that switch on the status string must treat the two new values as "could not check", not as success or as tampering. |
| Python `verify --anchors` coverage for an anchors file that is not in increasing `seq` order | `anchored_upto` is now the highest anchored `seq` (the format and the Rust verifier already did this); before, it was the seq of the last line, so the count of records after the last anchor could be too large. | Nothing to go back to: anchors written by `auditrail anchor` are always in increasing order, so existing files report the same numbers. |
| Parallel tool calls in one workflow (`PolicyEngine.admit`, used by `Guard`) | A call's categories are reserved when it is admitted, under a lock, instead of after it returns. Before, three tools started together (a model asking for several tool calls at once) each saw an empty history and all ran, completing the trifecta. Now exactly the call that would complete it is refused, whatever the order. A refused call is recorded as `deny` as before. | Nothing to go back to. Code that calls `PolicyEngine.check()` and `commit()` itself is unchanged; `Guard` uses the new `admit()`. |
| `RemoteLedger` after a lost reply | If the request was sent and no valid reply came back, `RemoteLedger` does **not** send it again: it raises `RecorderUnavailable` whose text starts `outcome unknown` and says the call may or may not have been recorded (check the ledger). It retries only a failure that happened before the request was on the wire (a refused connection, a failed send). Before sending on an idle connection it checks, with `select`, whether the recorder has closed it, and reconnects first, so the recorder's 300 s idle close does not cause a false error. Before, a lost reply made the same call appear twice in the ledger. | Repeat the call yourself after looking at the ledger. The idle check uses `select`, which behaves the same way on Windows and POSIX for this purpose; it was exercised on Windows only. A connection reset in the instant between the check and the send is reported as an unknown outcome. **Interaction with heartbeats:** a heartbeat whose reply was lost raises like any other failure, so the counts it carried are put back and the next heartbeat carries them again; if the first one had in fact been written, the same counts appear in two heartbeats (counted twice). That errs towards showing a mismatch (`UNRECORDED_CALLS`) rather than hiding one. |
| Recorder signs only fixed-shape records and marks client records (`recorder.py`, `_schema.py`) | A request with a wrong field set or wrong types (for example a non-hex `policy_hash`, `tools` that is not a list of strings, a count that is not an integer) is refused with an error and nothing is signed. Every record written on a client's request gets an additive field `origin` with the value `"client"`; records the recorder writes itself have none. The format version, the serialisation and the vectors are unchanged, and both verifiers read a ledger with `origin` fields as before. Before, such a request was signed and made the verifier stop at that record (`MALFORMED_RECORD`), and a forged heartbeat looked like the recorder's own. | Nothing to go back to for valid clients: every record the library itself writes passes. A hand-written request in another shape is now refused. |
| Recorder connection limits (`RecorderService`) | A request line longer than `max_line_bytes` (default 1 MiB) closes the connection, before the token is looked at and without buffering more than the limit; a connection idle or stalled for `connection_timeout_s` (default 300 s) is closed; more than `max_connections` (default 128) simultaneous connections are refused. `RemoteLedger` reconnects by itself after an idle close. Before, one line of any size was buffered in memory before the token was checked, and every connection took a thread. | The three values are arguments of `RecorderService(...)`; raise them there. The `auditrail recorder` command uses the defaults. |
| Appending to a ledger that does not end in a newline (`Ledger`, the recorder) | `LedgerTailError`: nothing is written and the file is not changed. Before, a torn last record made every later append fail, and a missing newline made the next record share a line with the last one. | Restore or move the file and start a new one; see "A ledger that ends in the middle of a line". There is deliberately no switch to append anyway. |
| `auditrail verify --anchors FILE` with a FILE that does not exist (Python CLI) | One line `[ERROR] FILE: file not found` (or `not a file` for a directory) on stderr and **exit code 2**, no result. Before: `OK`, as if no anchors had been made yet, which hid a mistyped path. A witness copy, or an anchors file that is a regular file but cannot be read (a lock, permissions), is `SINK_UNREACHABLE` (inconclusive, exit 1) instead of an uncaught error; a directory given to `--anchors` is an `[ERROR]` (`not a file`) with exit 2. | Leave out `--anchors` to verify without anchors. The library function `verify_anchors` still treats a missing file as no anchors; only the command line changed. |

Not changed: an empty category list is still not a declaration in strict mode, and without strict mode a tool with no
category still runs (with a warning when it is wrapped).


## Key custody (read this before trusting a signature)

1. Generate the recorder key where the agent cannot read it: `auditrail keygen --out keys/recorder`.
2. Run the recorder as its own process/OS user (`auditrail recorder --key ... --ledger ...`). Agents use `RemoteLedger`, which can only append and never sees the key.
3. Publish the **public** key (`recorder.pub`) with the first anchor, somewhere the operator cannot silently change. Verifiers pass it with `--pubkey`.
4. Publish anchors to a witness at a cadence that bounds how much tail you accept losing.
5. Rotate by anchoring under both keys for an overlap, then retire the old one.

## Version history of this document's claims

v0.1 said `verify()` "does not trust the process that produced the file". That was
wrong: a plain hash chain can be recomputed by anyone who can write the file
(demonstrated by `tests/test_signed_evidence.py::test_rewrite_and_rehash_passes_without_keys_but_fails_with_signatures`).
v0.2 fixes that with signatures and anchors and states the remaining conditions above.
Fuzzing the two verifiers against each other then found, and v0.2 fixes, readers that disagreed on odd input: a Python crash on non-UTF-8 files; signatures that could be altered with whitespace or capitals and still verify (`bytes.fromhex` is lenient); `true` accepted as the integer 1; `NaN`, `-0` and huge integers accepted by one reader; Unicode line breaks splitting records differently; lone surrogates crashing one reader. It also fixes: v0.1 ledgers being reported as tampered by the strict v2 reading rules (v0.1 stored a float `duration_ms`; they now get a distinct `LEGACY_FORMAT` result and an explicit, Python-only `verify --legacy-v01` hash-chain check, which is as weak as v0.1 always was). It also fixes: the deny-list environment filter (now allow-list), a printing tool
corrupting isolated results, raw error text reaching the ledger, concurrent
writers corrupting the chain, and heartbeat-less silent gaps.

## A ledger that ends in the middle of a line

If the process or machine stops while a record is being written, the file can end with half a record, or with a whole
record that has no newline after it. Appending to it would either fail for good (a torn record cannot be read back) or
put two records on one line, which the verifier then reports as `TAMPERED_LEDGER`: good evidence made to look altered.
`Ledger` therefore **refuses to append** to a file whose last byte is not a newline and raises
`LedgerTailError` (through a running recorder, the client gets an error reply; `auditrail recorder` started on such a file prints one `[ERROR]` line with the guidance and exits with code 2, without a traceback). It does not truncate or repair anything,
because any change to the file is a change to the evidence.

What to do: keep a copy of the file exactly as it is. Then either restore a good copy of the ledger, or start a new
ledger file and write down where the old one ends (the last anchor you hold from a witness shows how much of it is
covered). The verifier still reads a file that lacks only its final newline as the records it holds.

## Smaller known issues (not fixed)

- A workflow's categories live in the `PolicyEngine` until `end_workflow()` is called. A registered peer that sends many
  signed messages with different `trace_id` values makes that memory grow without bound.
- Calling `RecorderService.stop()` before `start()` blocks, because `shutdown()` waits for a server loop that never ran.
- The categories in an agent-to-agent message are declared (and signed) by the sender. A sender that leaves out a
  category it touched gives the receiver no way to inherit it: "a split trifecta is still a trifecta" holds only when
  senders declare honestly.
